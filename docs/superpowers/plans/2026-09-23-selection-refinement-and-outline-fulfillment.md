# 选区精修与章纲兑现清单

## 目标

在作者审核候选正文时，能只精修选中的片段，并在采纳前核对章节目标、钩子与伏笔是否在候选中得到体现。

## 约束

- 精修请求只读取当前候选、选段附近上下文和本章章纲；生成建议本身不写数据库。
- 候选 ID、候选文本 revision、UTF-16 选区偏移和选中文本必须同时匹配；冲突时不应用建议。
- 作者明确选择某个版本后，沿用候选文本 revision 写入 `candidate_text`；保留候选文本历史、重置旧审核和记忆提议，并重新审核。正式正文仍只能经原子 accept 事务写入。
- 章纲兑现检查是按需调用的非阻断辅助；报告不持久化、不改候选、不影响采纳按钮。
- 证据必须是候选正文的精确子串；不能定位的模型引用转为“需人工判断”，不能编造原文。
- 浏览器 API 使用当前请求的 Provider；Electron 使用白名单 IPC，由 Main/Vault 解析凭据。Provider key、提示词和原始异常不得落盘或进入公开错误。
- 精修调用归因 `repair` 阶段，章纲检查归因 `review` 阶段；两项都由作者主动触发。

## 验收标准

- 未选择片段或未填写精修要求时不能调用模型；生成后候选正文、revision 和审核状态保持不变。
- 生成 2–3 个备选；应用某一项只替换原选区，候选文本 revision 增加一次，旧审核清空并重新审核。
- 两个并发精修中，旧 revision 的建议无法覆盖新候选文本。
- 兑现清单为 objective、hook 和每条 foreshadowing 返回状态、说明和可定位证据；没有可验证引用时返回 uncertain。
- 兑现未完成不会禁用采纳，也不会自动更改候选或正式正文。
- `npm run lint`、`npm run typecheck`、`npm run test:run`、`npm run build`、`npm run e2e` 通过。
- 1440×960、1024×768、390×844 下没有文字裁切、抽屉重叠或页面横向滚动。
